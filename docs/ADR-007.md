# ADR-007 — Real Gujarat Police feeds via the Sentinel Camera Grid

Status: accepted (2026-09-26)

## Context

Gujarat Police provided 30 live cameras, published as the Sentinel Camera Grid at
`cctv.corp8.cloud`. The origin is password-gated: a form POST to `/auth/login`
(approved email + access password) sets an HttpOnly session cookie that must
accompany every request. The camera set is published at `/cameras.json` (the
source of truth — it can change) and each camera exposes HLS at
`/<id>/index.m3u8` (RTSP/WebRTC also exist for on-network AI clients; not used
for viewing). Each client gets its own stream copy; feeds loop with scene
discontinuities.

## Decision

1. **Server-side session, signed gateway unchanged.** The api container
   authenticates once (GRID_EMAIL/GRID_PASSWORD in `.env`) and holds the
   HttpOnly cookie in a process-wide client (`services/grid_client.py`),
   re-authenticating transparently on bounce-to-login. Browsers keep receiving
   only signed gateway URLs (ADR-005 holds; the origin URL and cookie never
   reach the client).
2. **Catalogue-driven onboarding.** `services/grid_sync.py` +
   `POST /streams/admin/sync-grid` upsert Module-1 cameras (`GP-CAM01`…,
   Police department, district inferred from the catalogue name) and HLS
   stream_sources (`vms_system='GP-GRID'`). Idempotent, re-runnable; entries
   removed from the catalogue are disabled, never deleted (audit trail).
   Registry camera codes for grid feeds (`GP-*`) are owned by the sync.
3. **Routing in the relay, not per-call plumbing.** `hls_service` routes any
   URL under the grid base through `grid_client`; all other origins keep the
   plain path with optional per-source headers via the new
   `stream_sources.auth_json` (migration 0003). The health prober uses the
   same routing, so real streams flip ONLINE within one probe cycle.
4. **No fabricated analytics on real feeds.** The simulated ANPR engine now
   queries `protocol='SIM'` only — real cameras never receive synthetic
   observations/events/alerts. Real ANPR remains a separate engine per ADR-006.

## Consequences

- Playback, health and onboarding work identically for demo and real feeds;
  LiveView's existing VMS filter separates `GP-GRID` from the SIM systems.
- **Watch-time quota.** The grid limits per-account watch time; exhaustion
  answers login with 403 "watch time limit reached". The platform detects it
  and backs off 30 minutes (`GRID_COOLDOWN`), probes grid cameras
  round-robin (2 per 45 s cycle ≈ each camera every ~11 min), and caches
  grid playlists for 30 s. **The viewer is click-to-start** (matching the
  portal's own click-to-play model): LiveView opens streams only on explicit
  user action, hls.js retries are capped at 6 and gateway refusals stop
  cleanly into a 'cooldown' tile state — no retry storms. Keep other grid
  viewers (e.g. the original portal tab) closed while the platform is the
  designated consumer: every client draws from the same account quota.
- Grid auth failures surface as `GRID_AUTH_FAILED` (502) at playback and
  `GRID_AUTH_EXPIRED` in probe details rather than generic upstream errors.
- The api container proxies segment bytes for every watched real tile; load
  scales with concurrent viewers, and probing is playlist-only (light).
- Grid credentials live in `.env` (server-side only); for production, use
  secret management and a dedicated read-only grid account.
